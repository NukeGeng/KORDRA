# FEAT-IAM-001 — Authorize scoped resource access

## User story / outcome
**Actor:** User / ServiceAccount / Agent. **Goal:** Authorize scoped resource access. **Primary owner:** `MOD-IAM`. **Phase:** MVP.

## Pre-conditions
Principal được xác thực; resource tồn tại và có owner rõ ràng.

## Main flow
Resolve verified identity → resolve owned resource → resolve valid grants → evaluate permission+scope+policy context → allow/deny + audit.

## Alternatives / exceptional flow
Grant revoked mid-operation: re-evaluate at execution. Platform role không mặc định được mở dữ liệu tenant.

## Messages and integration contracts
`membership.changed.v1; security.access.denied.v1`. Message names are candidates; verify owner/consumer in [message catalog](../../../contracts/message-catalog.md) before code. Stable envelope, retry and idempotency obey [messaging architecture](../../../architecture/messaging.md).

## Authorization / tenant-scope review
- Principal verified, permission key from [catalog](../../../contracts/permissions.md) and resource owner resolved from trusted store.
- The `organization_id`/scope is validated on read, write, event handler and any background job.
- Audit sensitive decisions with `actorRef`, `resourceRef`, `correlationId`, policy version.

## Negative & recovery scenarios
Role name Admin nhưng không có permission; body tenant bị đổi; expired token/grant; tự cấp quyền cao hơn.
- Generic tests: duplicate request/message, authorization revoked mid-flight, resource from another tenant, crash/restart, stale state/event, partial external failure where applicable.

## Acceptance criteria
Cross-tenant access luôn bị chặn; permission mới được thêm qua data-backed catalog không sửa if-role.
- No hard-coded role name; can add role templates without rewriting handler authorization.
- Linked tests and source commit evidenced before marking `implemented` / `verified`.

## Proposed technical tasks (not implementation evidence)
- Define command/query/API shape; validate domain invariants in owner module.
- Implement contract integration + tenant-safe query; write unit, contract, integration and failure tests.
- Add tracing/audit and update technical-debt / runbook if unresolved risk.

Proposed in-process responsibilities below are review inputs, **not adopted API, data or wire schemas**:

| Seam | Proposed input/authority and denial rule |
|---|---|
| Principal/session trust | An approved authentication boundary must supply verified principal/session identity and current validity/revocation evidence. Resolve status through its trusted owner; missing, invalid, expired, revoked or unavailable evidence denies protected access. A client assertion or cached login success cannot replace validation. ServiceAccount/Agent trust needs its own reviewed identity contract; local user accounts do not authenticate those actors automatically. |
| Tenant/resource ownership | Resolve active membership/tenant status from MOD-TEN and the requested resource's organization/project/environment/target association from its authoritative owner. Caller scope is only a requested selection, cross-checked against both; wrong tenant, suspended/missing ownership or unavailable/stale authority denies. No inference from labels, local profile or provider credentials. |
| Permission/policy evaluation | Combine trusted subject, current membership/grant facts, the action's existing catalog permission and permitted scope, authoritative resource chain, policy revision, time/expiry and relevant conditions. Require a valid scoped grant; deny overrides permit. For example, `target.read` retains its catalog project/environment scope while checking the particular target association. Role labels, parent scope and read permission do not imply other permissions. Missing policy/grant dependencies or unverifiable freshness deny. |
| Platform/support separation | Platform authority cannot read tenant payload. Tenant support requires a separately validated MOD-PAD delegated grant with exact resource/action scope, TTL, reason and required approval; missing/revoked/expired approval or grant denies. Do not invent an OP-P0 support bypass or default platform-to-tenant inheritance. |
| Revocation and disclosure | Revalidate session, membership/grant, ownership and policy before protected use and result disclosure, including delayed work. A permission change invalidates reliance on an earlier permit; re-evaluate at the execution boundary. Restart/reconnect cannot restore old authority by default. Exact freshness/concurrency guarantees require review; do not claim instantaneous cancellation of work already performed. |
| Decision/audit boundary | Return only disclosure-authorized decision metadata; correlate actor/resource, policy revision, reason and outcome with MOD-AUD. No passwords, session credentials or tenant existence leaks in errors/logs/audit. Unavailable mandatory authorization evidence denies; if required audit cannot be recorded, do not proceed with the protected action. Exact durable audit/outage behavior remains a decision. |

### I2.2 — In-process input and owner-result proposals

All names below are **semantic placeholders**, not concrete classes, serialization names, schemas, cryptographic receipts or storage fields. `ref` means an opaque typed identifier, `revision` an owner-defined change identity, and `instant` a trusted UTC time under a clock policy still to be approved. Identifier encoding/length limits and comparison rules require owner agreement; the proposed semantic rule is nonempty, bounded, exact opaque equality, without case folding, prefix matching or label substitution. Unknown enum values, malformed records and ambiguous optional values deny. No passwords, bearer/session credentials or provider secrets belong in these inputs/results.

| Proposed value / input | Fields and result meaning / validation |
|---|---|
| `AccessSelection` (untrusted) | `requestedTargetRef`, `requestedTenantRef`, `requestedScopeKind`, `requestedScopeRef`, optional `selectionRef`. These select what to resolve; they cannot supply principal, membership, owner, policy, time or revisions. Server use-case mapping supplies `action = target.read`; caller permission text cannot enlarge it. A caller revision is only a stale-selection hint to compare, never evidence of currency. |
| `AuthenticatedInvocation` (trusted boundary input) | `invocationRef`, `principalRef`, `principalKind`, `sessionRef`, `authenticationContextRef`, `deadline`. Must come from the approved authentication boundary, bound to this invocation and its session subject; caller principal/session IDs or a pasted owner-result structure are rejected as authority. `authenticationContextRef` is an internal reference, not a reusable credential. Deadline is server-bounded, cannot extend any authority lifetime, and cancellation/timeout denies. Authentication mechanisms remain undecided. |
| `AuthorityLookup` (trusted internal request to each owner) | `invocationRef`, expected typed subject/session or resource refs, the selected tenant/action/scope where relevant, and server-bounded deadline. Each owner resolves its own facts and returns evidence bound to these exact lookup keys; an echoed request is not a successful resolution. Lookup success is not permission to disclose its metadata to the caller. |
| `OwnerEvidence<T>` (common owner result) | `outcome = resolved / notFound / unavailable / unknown / invalid`, `ownerRef`, exact `lookupBinding`, and, only on `resolved`, `facts`, `revision`, `observedAt`, `notBefore`, `expiresAt`, `revocationEvidenceRef`, `consistencyEvidenceRef` where required by the eventual protocol. Required evidence cannot be null/blank or of another owner/type. Owner identity is established by approved trusted composition, not the `ownerRef` string. Partial, conflicting, future-dated beyond approved tolerance or stale results deny. Non-resolved results carry no caller-visible existence detail. |
| `PrincipalSessionFacts` (IAM) | `principalRef`, `principalKind`, `principalStatus`, `sessionRef`, `sessionSubjectRef`, `sessionStatus`, separate principal/session revisions, validity intervals and revocation evidence. Require the authenticated User and session subject to agree exactly; require active principal and session, no revocation, and current validation from the owner. A fixture's `Validated = true` or `Revoked = false` proves none of this. Unsupported principal kind denies. |
| `TenantMembershipFacts` (TEN) | `tenantRef`, `tenantStatus`, `membershipRef`, `memberPrincipalRef`, `membershipTenantRef`, `membershipStatus`, tenant/membership revisions, validity intervals and revocation evidence. Require active tenant and membership, exact principal and tenant agreement, no suspension/revocation. Being a member of two tenants does not merge scopes. A fixture's `Active` boolean cannot establish current tenant status. |
| `ScopedGrantFacts` (assignment/definition owners to agree) | `grantRef`, `subjectRef`, `tenantRef`, `permissionKey`, `scopeKind`, `scopeRef`, `grantStatus`, validity interval, assignment and RoleDefinition revisions, revocation evidence and owner provenance. For this candidate require one resolved effective grant, exact `target.read`, exact project/environment scope, active status and no revocation. Role labels confer no authority. No union, inheritance, implicit organization/platform scope or conversion between project/environment is proposed. Ambiguous grant/definition resolution denies. |
| `TargetOwnershipFacts` (INV) | `targetRef`, `tenantRef`, `projectRef`, optional `environmentRef`, owner lifecycle eligibility, target revision and association references. Require the requested target and tenant exactly; deleted, disabled, ambiguous or unresolved ownership denies. Which owner lifecycle states permit reading remains an explicit owner decision. This record cannot attest the PRJ side of an association. |
| `ProjectEnvironmentFacts` (PRJ) | `projectRef`, `projectTenantRef`, project revision/eligibility; when an environment is associated, `environmentRef`, `environmentProjectRef`, `environmentTenantRef`, environment revision/eligibility, classification, policy association and `targetBindingRef`/binding revision linking the exact target. Resolve every present link on both sides. A project-only target needs an explicitly resolved absence of environment, not a failed environment lookup. Environment scope requires a present matching environment. |
| `EffectivePolicyFacts` (IAM plus relevant owners) | Exact action/resource/scope binding, effective policy/catalog revisions, referenced owner-policy revisions, complete applicable deny evaluation, required conditions, validity interval, freshness/clock rules and `auditRequirement`. Require all applicable policy inputs; absent deny data is unknown, not “no deny.” Any explicit deny wins over a grant. Unresolved/unsupported conditions deny. Audit requirement cannot be selected or downgraded by the caller; unknown audit policy denies. |
| `EvaluationInput` (assembled internally) | `AuthenticatedInvocation`, original `AccessSelection`, all required owner evidence, trusted `evaluatedAt`, bounded deadline, and the proposed consistency context for this invocation/stage. Caller principal/tenant/scope/revision cannot replace any owner fact. Do not expose an endpoint accepting this structure, or extract the I1 records as runtime input validation. |

Every required revision must be compared to its current authoritative counterpart under the **approved consistency protocol**, including principal/session, tenant/membership, grant/definition, target, project/environment/binding and effective policy. Nonempty strings, equal cached revisions, timestamps, an owner's optimistic `Available` flag or a caller's version do not prove current authority. `observedAt` records an observation; `expiresAt` bounds usability, not a no-revocation guarantee. The meaning, issuer, validation, restart behavior and lifetime of `revocationEvidenceRef` and `consistencyEvidenceRef` are `[NEEDS-DECISION]`; until resolved, these names confer no trust and cannot satisfy runtime prerequisites.

### I2.3 — Validation, result and disclosure boundary

The proposed evaluator denies unless **all** required evidence is resolved, well formed, owner-trusted, current and coherent for this invocation. Validate independently, without changing the selection to make a match:

1. Match invocation principal = session subject = membership principal = grant subject. Match requested tenant = target tenant = project tenant = membership tenant = grant tenant, plus environment tenant when present. Match requested target = INV target = PRJ target binding when present. Match INV project = PRJ project, and any INV environment = PRJ environment whose project/tenant match that chain. No foreign-scope association may be accepted by matching a display label.
2. Match requested/granted scope kind and ID exactly. Project scope ID equals the resolved project; environment scope ID equals the resolved environment. The project chain is required in both cases. For an environment-associated target, validate the binding even for project scope. Platform authority never substitutes for tenant evidence; unsupported support/approval paths deny, including expired approval.
3. At each protected boundary use trusted time and the approved skew/clock policy. Require `notBefore <= now < expiresAt` for each applicable interval and `now < deadline`; equality at expiry denies. Enclosing evidence cannot outlive any underlying session/membership/grant/policy/consistency validity. Missing time, unbounded or inverted required intervals, clock rollback/uncertainty outside policy, revocation, inactive/suspended state or freshness uncertainty deny. No arbitrary TTL/skew allowance is selected here.
4. Require current policy/owner revisions and complete condition evaluation under I2.4. Explicit deny, scope mismatch or failed required condition overrides any positive grant. No failure, exception, unknown response, timeout or audit/authority outage may default to permit. A structurally valid record cannot supply missing provenance or consistency.

| Proposed result / consumer | Fields and boundary |
|---|---|
| `EvaluationResult` (internal IAM → enforcement only) | `verdict = deny / eligible`, `invocationRef`, server-created `decisionRef`, stage (`beforeUse` or `beforeDisclosure`), and on eligibility only the exact subject/session/tenant/action/target/scope binding, owner revision set, evaluation time, upper validity bound and audit obligation. `eligible` is a candidate for this boundary only: it is not a bearer capability, durable authorization, final public success or permission to skip audit/consistency enforcement. A cached or replayed result cannot authorize another invocation, stage or resource. |
| `PrivateDiagnostic` (restricted) | One fixed-category reason such as `authorityInvalid`, `scopeMismatch`, `expiredOrRevoked`, `consistencyUnknown` or `auditUnconfirmed`, plus server decision/invocation correlation. Cap reason count and record size under an owner-approved budget; no raw exceptions, request text, attacker-supplied identifiers, record dumps, credentials, policy contents or foreign-tenant existence/detail. Specific cause analysis requires separately authorized owner tooling. Numeric budgets/access/retention are unresolved; unrestricted logging is not a fallback. |
| `PublicDenial` (caller boundary) | One opaque denial shape, without reasons, owner outcomes, subject/tenant/resource IDs, revisions, audit availability or existence distinctions. Optional correlation must be server-created, non-enumerable and confer no read authority; its format remains undecided. Missing target, wrong tenant, missing permission and unavailable evidence produce the same denial shape. Protect status/body/header/size behavior and avoid extra existence-probing lookups; timing leakage requires later measurement/mitigation, not a claim of constant-time behavior. Existing bootstrap empty 403 behavior is unchanged. |
| `AuditAppendIntent` (trusted producer → AUD) | Server `decisionRef`/idempotency ref, invocation correlation, stage, evaluated verdict, bounded category and policy/revision references; trusted subject and resource refs only when authorized for that audit scope. Unresolved/foreign requested IDs are omitted, never echoed. Bind the intent to this exact decision and enforcement stage; do not log a completed operation from eligibility. Audit of denial must itself avoid creating a cross-tenant existence oracle. |
| `AuditAppendResult` (AUD → enforcement) | `durable / rejected / unavailable / unknown`, and only for a durable result, owner-issued record reference bound to the exact intent, scope and decision. An availability probe, enqueue-in-memory success or `Available = true` is insufficient. Durability, idempotency, acknowledgement-loss lookup and any approved durable outbox acceptance semantics remain AUD decisions. Unknown receipt cannot be guessed successful. |

The enforcing consumer must withhold protected dispatch and data release until required current authorization, consistency and durable-audit conditions for that stage are satisfied. If policy requires durable audit, lack of confirmed durable acceptance denies that operation/disclosure; “audit later” is not a fallback. Denial stays opaque even when its own audit fails. Bounded private operational failure reporting must not expose tenant data or recursively require a permissive audit authorizer. Audit coverage of attempts versus results, commit ordering and crash reconciliation must be agreed; an append alone neither authorizes the action nor proves it completed. If audit waiting changes authority, restart/revalidate the affected boundary and bind any new audit intent to the new decision; an old receipt cannot cover changed scope/policy. No durable audit mechanism or cross-module transaction is selected here.

### I2.4 — Freshness, concurrent revocation and protected-use prerequisites

Proposed protected boundaries are **before protected use** (including provider dispatch or protected cache access) and **before any disclosure** (including delayed results, cached data, exports or a later page/chunk). The trusted enforcement consumer owns these boundaries; IAM owns evaluation, each authority owner owns its facts, and AUD owns audit durability. Internal ownership resolution must itself have a reviewed trusted access boundary and disclose no metadata to the client.

Sequentially reading each owner, then re-reading revisions just before sending data, still leaves races during reads and between the final check and use. A revision vector is diagnostic binding, not an atomic snapshot, a revocation fence or proof that all facts were simultaneously valid. A fresh timestamp or a successful audit append does not close that gap either. **No runtime permit is justified until an approved consistency protocol defines a coherent decision/use boundary across the participating owners and enforcer.** This document invents no cross-module transaction and promises no instantaneous revocation.

Before adoption the assigned owners/security reviewer must define: which changes invalidate authority; the decision/use and disclosure ordering points; how conflicting owner versions, target reassignment and concurrent revoke are detected or excluded; the lifetime and enforceability of any consistency evidence; clock/partition/time-out behavior; and what happens when revoke races with an already-started read or a partially disclosed response. The protocol must explicitly distinguish revoke effective before the protected boundary (deny), revoke after an already completed boundary (cannot undo prior disclosure), and ambiguous ordering (withhold further use/disclosure). Any permitted in-flight window requires explicit human acceptance and a bounded guarantee; it cannot be inferred from a cache TTL. A “final recheck” without enforceable ordering is insufficient.

When a revision/status changes, cancellation, expiry or uncertainty occurs, discard eligibility and re-resolve required authority for any new attempt; no permissive stale fallback. Discard unauthorized delayed results and do not publish them into caches accessible under another subject/selection. Reconnect/restart, duplicate requests and stale invalidation events cannot resurrect authority. Caches may optimize resolution only within the reviewed protocol and must still revalidate protected boundaries; cached decisions are never sufficient. Current checks cannot retract bytes already released, so streaming/partial disclosure is excluded from the first adoption scope. Crash/unknown execution or audit outcomes require reconciliation, not automatic replay of protected work. Later side-effecting workflows need their own idempotency, inbox/outbox, retry and unknown-outcome contracts; this in-process proposal adds no message semantics.
