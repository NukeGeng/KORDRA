# Release and approval v1 — exact T11 proposal

Normative accepted T11 contract for FEAT-APR-002, FEAT-REL-001 and FEAT-APR-001 under [ADR-0005](../decisions/0005-immutable-release.md). **Accepted by NukeGeng on 2026-10-27 for T11.0–T11.3; implementation remains pending.** Baseline is `main@bc91c2a66abcdb2156363f5fdbd3dc7f89046e67`, containing owner-merged [PR #19](https://github.com/NukeGeng/KORDRA/pull/19). At the inspected main baseline REL/APR contained reserved README files; a local APR Domain increment is now in progress. T10 code, current IAM/TEN/PRJ/INV/AUD and their accepted contracts are preserved.

This contract owns T11 rules; feature documents own use cases and evidence. The wider [release/execution proposal](release-execution-v1.md) retains future execution/worker design only. Design acceptance does not establish implementation, runtime activation, grants or real migration authority.

## 1. Useful outcome and approval meaning

A user selects a registered immutable artifact and an active application/environment/target in one trusted project, reviews the server-resolved selection, freezes a release revision, requests approval and sees a durable grant/rejection/revocation with current eligibility. A solo Development/Test pilot can explicitly configure self-approval. History survives API restart; browser sessions retain their existing boot invalidation.

The frozen subject is **`release-intent-v1`**, not an executable deployment plan. It covers every T11-selected field. Driver version, remote cluster/namespace identity, chart/package, rendered resources, runtime configuration, secret-binding revisions and health policy do not exist in the adopted T11 model and must not be fabricated as valid null/default values. T12/T13 must bind those additional facts to a separately versioned execution-plan hash and obtain its own authorization/approval before dispatch. A T11 approval cannot approve later-added fields or serve as a worker credential. Every T11 projection declares `executionAuthorized=false`; there is no execute/deployment endpoint, 202 operation promise, provider request, credential read, broker message or outbox publication.

Use `release.approve`, not `deployment.approve`, for this subject. The latter and `deployment.override` remain unadopted. This explicit distinction refines the unaccepted 2026-10-20 sketch; it does not weaken an accepted deployment contract. An approved release intent may be a future reviewed input, never sufficient execution authority.

T10 supplies `manifest_config_hash_verified`, `layerAvailability=not_checked`, `signatureVerification=not_checked`. Its source declarations are per-registration and unverified; do not borrow another principal's receipt or turn a claim into CI evidence. T11 copies immutable artifact facts only and records `provenanceClass=unattested`. Its initial `pilot` qualification permits freeze/request/grant only for Development/Test under an explicitly permitting policy. Staging/Production drafts can be recorded for planning, but freeze/approval returns `qualification_required` until a future accepted verification/execution profile exists. No fresh pull, registry availability, hardware compatibility or signed provenance is inferred from historical ART data.

## 3. Approval policy v1 — FEAT-APR-002

Policy administration is a stopped-installation maintainer operation using the existing private identity/OS lock, exact inspect/apply manifest hash and `kordra_admin`. It has no HTTP endpoint and no role-based public policy-management permission. It neither reads Keychain nor contacts a target. Missing policy never falls back to a built-in permitting policy.

An immutable policy revision has exactly: `schemaVersion=1`, `purpose=release-intent-v1`, `status=active|inactive`, `effectiveFromUtc`, nullable `expiresAtUtc`, `rules`. Tenant/project/policy ID/revision are immutable owner metadata. Require one current head per `(installation,tenant,project,policyId)` and one APR binding per `(installation,tenant,project,environment,purpose)`. Policy revisions and binding revisions strictly increase; binding IDs are unique and stable across replacement, never reused for another scope. Bind only an actual active PRJ environment with matching classification. Do not overload PRJ's `target.read` binding table.

Each rule has exactly `classification`, `effect`, `separationOfDuties`, `allowUnattestedProvenance`, `pendingLifetimeSeconds`, `grantLifetimeSeconds`, `blockedWindowsUtc`. Classification is Development/Test/Staging/Production; effect is allow/deny. Require 1–8 rules, no duplicate `(classification,effect)`, ordinal classification/effect sort; deny overrides allow and no applicable allow denies. Every rule must parse even when it would not match. Allow rules use `independent` or `self_allowed`; deny rules require `independent` and `allowUnattestedProvenance=false`. `self_allowed` and `allowUnattestedProvenance=true` are legal only for Development/Test. V1's pilot profile still denies Staging/Production freeze/approval even if a policy rule says allow; policy cannot upgrade artifact qualification.

Both lifetime integers are 60–86,400 seconds. Recommended explicit pilot values are pending=86,400 and grant=1,800; there is no omitted-field default. At most 16 blocked UTC windows per rule, each exactly `{startsAtUtc,endsAtUtc}`, finite half-open intervals with start < end, sorted ascending and nonoverlapping. No recurrence, local timezone/DST expression, shell, plugin, arbitrary condition, quorum or emergency override. Requesting can queue during a window; granting cannot occur inside it. A grant made before a future window expires no later than that window's start and cannot resume after the window.

The closed offline manifest has exactly `schemaVersion=1`, `manifestId`, `installationId`, `expectedDatabase`, `expectedRole=kordra_admin`, `tenantId`, `projectId`, `policyId`, `expectedPolicyRevision`, `payload` and `bindingChanges`. A new policy requires expectedPolicyRevision=0 and receives revision 1; publishing requires the exact current positive revision and allocates its checked successor. `bindingChanges` has 0–32 items, sorted by canonical environmentId, each exactly `environmentId`, `expectedEnvironmentRevision`, `expectedBindingId` and `expectedBindingRevision`. For a new binding require explicit null/0 respectively; for an existing binding require its exact ID/positive revision, even when replacing a different policy. Each item binds the resulting new policy revision; no implicit upgrade of unlisted environments. An inactive payload can invalidate listed bindings but never authorize their use. The policy head advance also invalidates old unlisted bindings; they do not float to the new head. Binding creation/replacement checks the current PRJ classification and records the complete tenant/project/environment and policy identity. Empty bindingChanges creates/publishes/deactivates a policy without implicitly upgrading any binding. Repeated IDs and bind-only operations are outside this v1 manifest; publishing another immutable revision is the explicit way to rebind. `expectedDatabase` is the actual approved loopback installation database, not a connection string or caller override of installation identity. Reject unknown/duplicate fields, noncanonical IDs/times, repeated environment IDs, partial binding edits and stale heads. New/revised policy plus all selected bindings, exact command receipt, AUD mutation and IAM clock floor commit once on the shared owner connection. Replay verifies the stored result and exact audit receipt; unknown commit fences. No policy/binding/role is provisioned by startup or migration. Deactivation/rebinding invalidates dependent eligibility; old payloads/bindings/audit are retained. Rollback cannot restore an older head or erase history.

Policy canonical bytes are compact UTF-8, recursively ordinal-sorted object keys, sorted rules/windows and explicit nulls. Hash is SHA-256 of UTF-8 `release-approval-policy-v1` + LF + canonical payload. Binding digest is SHA-256 of `release-approval-binding-v1` + LF + the canonical object with exactly installationId/tenantId/projectId/environmentId/purpose/bindingId/bindingRevision/policyId/policyRevision/payloadHash. These internal hash inputs are not new public response fields. The stopped manifest has a separate domain `release-approval-policy-command-v1` and binds every manifest field. Schema timestamps are exact UTC with six fractional digits and Z; reject submicrosecond or alternate-offset input rather than trimming it into acceptance.

Offline command shapes are `approval-policy inspect PRIVATE_MANIFEST PRIVATE_ADMIN_LOCATOR` and `approval-policy apply PRIVATE_MANIFEST PRIVATE_ADMIN_LOCATOR APPROVED_SHA256` in the existing Kordra.Api executable. They do not exist yet. Inspect is read-only, returns exactly schemaVersion/manifestHash/currentPolicyRevision/bindings (at most 32 selected binding identities/revisions), and records no grant or receipt. Apply requires that exact manifest hash and stopped canonical installation custody. Its safe result contains schemaVersion/manifestId/policyId/policyRevision/payloadHash/commandId/replayed only. Repeating the same apply reconciles an exact stored command/AUD result before mutable head/expiry validation; it does not republish or rebind. Missing or conflicting owner/AUD evidence stays fenced. The hash parameter is a content precondition, not proof of who approved it; maintainer operational authorization is independently required.

## 4. Release identity and exact frozen bytes — FEAT-REL-001

REL allocates a nonempty `releaseId` for a project lineage and a distinct `releaseRevisionId` plus monotonically increasing `revisionNumber`. A lineage may have at most one Draft. Creating its next Draft names an exact prior Frozen/Retired base revision in that lineage and serializes the next number with a unique database constraint. No automatic latest selection, clone of approval or deletion of history. Editing a Draft changes its `version` CAS counter, not its revision ID. Only its original creator with current `release.create` may edit/freeze it. Any current `release.retire` holder may retire a Frozen revision.

Persisted transitions: Draft → Frozen → Retired. Draft replacement is permitted only with the exact version; Frozen bytes and their hash are never rewritten. Retired is terminal. A changed selection after freezing creates another revision. Newer revisions do **not** silently invalidate older approvals: each action names an exact revision. Mark obsolete revisions Retired or revoke their approval explicitly; selecting an old revision is never an alias for latest.

Draft input consists of a label and exact application/environment/target/artifact IDs. There is no deployment configuration, chart, arbitrary JSON/YAML, URL, CLI, secret reference, template or annotation bag. Labels are metadata, 1–128 Unicode scalar values, NFC and no controls; reject malformed/non-NFC input rather than silently transforming it, and exclude labels from the canonical subject. No text normalization affects an authority ID/digest. Reason fields use the closed codes in section 7, not free text. Request/audit logging never captures raw input. A Draft can be saved against a known valid owner chain even when no permitting APR policy/qualification exists; its preview is ineligible and has no positive selectionHash. Freeze cannot bypass that missing basis.

Freeze resolves and pins this exact closed structure:

| Field | Frozen value |
|---|---|
| `schemaVersion`, `subjectKind` | `1`, `release-intent-v1` |
| `tenantId` | Trusted project owner tenant. |
| `project` | Exactly `id`, `revision`. |
| `application` | Exactly `id`, `revision`; active and in that project. |
| `environment` | Exactly `id`, `revision`, `classification`; active and in that project. |
| `target` | Exactly `id`, `kind`, `revision`, `associationRevision`; INV/PRJ agree on that exact environment. Local registered identity is not remote cluster identity. |
| `artifact` | Closed copy of ArtifactV1: artifactId, projectId, registryId, repository, rootDigest, platform, rootMediaType, rootSizeBytes, selectedManifestDigest, selectedManifestSizeBytes, selectedManifestMediaType, configDigest, configSizeBytes, observedPlatform, variantEvidence, verifierProfile, verifiedAtUtc, createdAtUtc, contentVerification, layerAvailability, signatureVerification. No automatic addition when ART later gains fields. |
| `approvalPolicy` | Exactly policyId, policyRevision, payloadHash, bindingId, bindingRevision. |
| `qualification` | Exactly `profile=pilot`, `provenanceClass=unattested`, `executionAuthorized=false`. |

All IDs are nonempty lowercase D-form GUIDs; revisions and sizes are positive checked integers; digests/platform retain accepted ART semantics. All object keys, including nested ART fields, are emitted in ordinal order. UTF-8 with literal non-ASCII scalars; escape only JSON-required quote/backslash/control characters, controls as lowercase six-character \u00xx (no optional slash/HTML/ASCII escaping), no BOM/whitespace, explicit schema nulls, no duplicate/unknown keys, no floating-point/nonfinite values. Timestamps are six fractional digits UTC Z, with no silent precision loss. No release/actor/request IDs or mutable display names are added to subject bytes. The same exact content can have the same hash in different revisions, but approvals additionally bind the distinct releaseRevisionId and therefore cannot transfer.

`specHash = lowercase SHA-256(UTF8("release-intent-v1") || LF || canonicalSpecBytes)`. Store exact canonical bytes (not only JSONB's reserialization) and hash, max 64 KiB. Re-read/recompute before accepting a frozen reference, returning it or granting approval. A mismatch is integrity failure, 503 and blocked admission pending stopped reconciliation, never recanonicalized in place. Tests must generate independent byte-exact vectors, reject malformed stored content and prove an execution schema cannot be accepted as this subject or vice versa.

Draft responses supply a bounded current owner selection preview and `selectionHash`. It is lowercase SHA-256 of UTF-8 `release-selection-v1` + LF + the canonical object with exactly `releaseRevisionId`, `version`, and `specHash` (the freshly computed candidate release-intent hash). This transitively binds the exact candidate spec bytes and draft identity/version without embedding an escaped JSON string. Freeze requires `expectedSelectionHash`; recompute it from fresh owner facts and exact Draft version. A mismatch is 409 so an owner/configuration change cannot silently freeze a different selection than the user reviewed. The client hash is a comparison precondition only; the server computes the authoritative bytes/hash. Missing/ineligible selection has no positive preview hash.

## 5. Approval request, decision and continuing validity — FEAT-APR-001

An approval request names one exact Frozen revision, specHash, tenant/project/application/environment/target/association, artifact identity, qualification and APR policy/binding. The requester is the current authenticated principal, never a body field. At request creation re-resolve all frozen owner revisions and qualification, recompute bytes/hash and require current policy/binding equal to the frozen selection. Changed catalog/policy facts require a new reviewed release revision; do not silently rebind the old one.

Require `release.request-approval` at the exact environment and `release.read` at the project. Record current requester principal/security/membership and exact assignment/definition/provenance revisions for both permissions. There is at most **one request ever per releaseRevisionId** in an installation; database uniqueness enforces it. Same key/input replays. A different key cannot replace a request or grant twice. After rejection, revocation, expiry or invalidation, create a new release revision (content may be copied/reviewed) to request again. This intentionally avoids approval resurrection and ambiguous parallel approval histories.

Recorded state starts Pending and transitions exactly once to Granted, Rejected or Revoked; Granted can transition once to Revoked. Every decision is an append-only immutable record; the state/head row is only an indexed projection updated with CAS. Rejection, revocation and grant entries cannot be edited or deleted. Grant/reject compete on the same Pending version; one wins. Concurrent grant/revoke is linearized by the shared gate/CAS: a grant can commit before a later revoke, which makes it unusable, or a revoke wins and no grant follows. No automatic re-grant.

Grant/reject requires current `release.approve` plus approval-read at the exact environment. Revoke requires current `release.approval.revoke` plus approval-read, including when the requester or original approver is the actor. Grant additionally checks current valid requester proof, active approver/member, all denies, exact frozen owners, policy/binding and deadline. Under `independent`, requester and approver principal IDs must differ; account labels and role names are irrelevant. Under explicit `self_allowed`, one principal may perform both only in Development/Test and only with both independently granted capabilities. A solo maintainer controls policy/role provisioning; this is not a claim of independent organizational production approval.

Pending expires exclusively at the earliest of request time + policy pending lifetime, policy expiry and original requester assignment expiries. A grant expires exclusively at the earliest of its original pending expiry, grant time + policy grant lifetime, policy expiry, original requester/approver assignment expiries and the next blocked window start. Persist the chosen absolute deadlines. No later extension, refreshed login, renewed grant, restart or retry extends them.

Keep `recordedState` separate from `effectiveState`. After current reader authorization, a recorded Rejected/Revoked remains that terminal effective state, with eligibilityReasonCode=rejected or revoked respectively (safe non-authority summaries). For recorded Pending/Granted, evaluate expiry first, then known invalidation, then current policy window; otherwise keep the recorded state with eligible. A current blocked window reports Pending with approval_window_blocked, never Granted; a prior Granted has already been capped to Expired at that window start. Never label terminal denial as a current grant. Temporary dependency unavailability needed to establish an active Pending/Granted state is 503. At or after an original deadline return Expired. A known inactive/changed principal, membership, assignment/definition, frozen owner revision, retired release or policy/binding yields Invalidated. A known absent record whose original immutable identity is present is invalidated; an unavailable or ambiguous reader yields 503, never a guessed invalidation or grant. Expired/Invalidated is computed from retained original evidence; it does not claim a new persisted decision or require a scheduler. Monotonic owner revisions prevent change-and-restore from resurrecting it. Readonly display is not a transferable permit. Explicit revoke may close an otherwise expired/invalidated record, but it cannot grant or extend it.

Original requester/approver **session tokens are not durable approval credentials**. Sessions are required for the actual HTTP action and its D handoff; after commit, ordinary logout/browser closure/API restart does not itself erase the decision. Continuing validity uses their persisted principal/membership/exact grant revisions and original expiries, with current owner/policy facts. Revoking those assignments invalidates eligibility. Add neutral IAM/TEN durable-eligibility owner ports for those exact original principal/security/membership/assignment/definition snapshots, adapted by Host; they do not issue a sessionless HTTP/action permit. They exclude boot/session revision from durable decision eligibility and still check current deny/revocation/expiry. Do not inspect another owner DbContext or mint a synthetic session. No session reference, cookie or bearer value enters stored subject/approval/audit records or worker messages.

Historical release/approval reads still require the reader's fresh scoped authority and current resource ownership. They can show Retired, Expired or Invalidated history without requiring the old policy to be permitting. Approval-read deliberately reveals only the full bounded frozen subject for its environment, not unrelated project releases, declarations, endpoints, addresses or credentials. On an unavailable eligibility reader return a bounded 503 rather than displaying a previously cached Granted state as current.

## 6. Transactions, idempotency and recovery

Remain one enforced API process with the existing installation lock, fair reader/writer gate, trusted clock/floor and shared capacity 16. No new coordinator service, queue, cache, helper pool or writer. Every invalidating owner/policy/retirement/approval writer participates in the existing writer registry; offline changes require API stopped. No direct live SQL writer or second API replica is supported.

Every online mutation validates current subject/permissions and owner selection under the write gate, checks its scoped idempotency receipt, applies exact CAS and stages owner rows + immutable decision/command receipt + AUD mutation + IAM floor on the same approved PostgreSQL connection/transaction. No independently committed cross-owner success. Recheck current time/earliest validity after audit staging immediately before commit. Policy publication and binding changes use the stopped equivalent. Owner handlers stage changes only; Host controls the single transaction. No arbitrary callback can bypass an owner invariant.

Key grammar is 16–128 ASCII letters/digits/dot/underscore/hyphen. Hash scope includes schemaVersion, installation, trusted tenant, principal, action and exact route resource. The scoped key hash is lowercase SHA-256 of `release-command-key-v1` + LF + a canonical object with exactly schemaVersion=1/installationId/tenantId/principalId/action/resource/idempotencyKey. `resource` is the exact canonical API route path (no query), `action` the exact operation name (create-draft, next-draft, replace-draft, freeze, retire, request, grant, reject, revoke). This hash is private. The business hash is lowercase SHA-256 of `release-command-body-v1` + LF + a canonical object with exactly `body` and `ifMatch`; body contains every accepted business field including schemaVersion, but excludes correlationId; ifMatch is the exact strong ETag or explicit null when unused. Include action/resource through the scoped key, never a client tenant/hash authority. Correlation is excluded. Same key/identity returns the authoritative current result after fresh action authorization; a stale original If-Match is tolerated only for an exact confirmed replay, never for a new write. Changed input is 409. A key never grants authority. Keep receipts/decisions indefinitely in this version; no purge/reset endpoint. Receipt content/audit disagreement is unknown, not permission to replay a mutation.

After confirmed M, obtain fresh read admission for D, re-resolve caller/scope/selection and current eligibility, durably audit the bounded result hash/size and floor, then recheck time immediately before headers/body. Retain admission through bounded handoff as in the accepted contract. A denied D withholds the body but preserves a confirmed mutation. Read U/D uses a bounded candidate set and fresh comparison at D; do not reuse a target-read permit. Missing/failed audit denies. Known pre-commit setup/cancellation rolls back without poisoning unrelated auth. Only an actually attempted unresolved commit, unresolved task or unknown handoff ownership fences as in the existing protocol. Do not claim successful rollback after an ambiguous commit.

Mutations finish in one database transaction, so T11 introduces no user-visible Pending operation/job receipt. Pending is an approval business state, not a background action. On lost ACK, abort/return safe unavailable without a success record; a fresh, stopped reconciliation inspects the exact installation/scoped key hash/business hash and owner/AUD receipt, including its server command/intent IDs. The operator may derive the scoped hash from the private original key and known actor/action/resource; no unknown random command ID is required just to locate evidence. Confirmed state may be reported unchanged; confirmed no-commit allows only an explicit operator/new HTTP action after fresh authority, not automatic replay. Missing/contradictory evidence stays fenced. Recovery never creates a grant, rewrites a Frozen spec, changes a decision, restores an old policy/head or dispatches anything. It loads no registry configuration/TLS key/Keychain; use the existing minimal stopped-custody pattern and trusted offline clock.

Online receipt recovery uses `release-recovery inspect|apply` or `approval-recovery inspect|apply` followed by private plan/admin-locator paths; apply additionally requires APPROVED_SHA256. Proposed plan fields are exactly schemaVersion=1/planId/installationId/bootId/oldProcessId/tenantId/principalId/action/resource/scopedKeyHash/businessHash/receiptHash/auditHash. Initial receiptHash/auditHash are explicit null; inspect under stopped custody binds them to exact durable evidence or a canonical no-commit evidence snapshot, without writing state. It returns the bound plan and its domain-separated `release-recovery-plan-v1` SHA-256. Apply rechecks that hash, absence of the old API and other installation writers, and unchanged complete owner/AUD evidence, then reports confirmed or no_commit with safe command/intent references only; it mutates no business row. Missing/contradictory evidence returns unknown and does not certify readiness. No destructive unlock or force flag is provided. A complete stopped recovery runbook, canonical evidence vectors and new-process startup readiness tests are required in the owning feature before these commands are called implemented. Only a fully stopped, verified-quiescent process may clear an old in-memory uncertainty fence; this cannot clear a persisted integrity disagreement. No helper/provider is invoked by T11 recovery.

## 7. Closed HTTP v1 surface

Existing local HTTPS `localhost:5128`, session cookie, exact Origin, CSRF on unsafe requests, strict framing, no forwarded-authority bypass and no-store apply. Default health-only host is unchanged. IDs are canonical lowercase D-form, no query override or tenant/actor/hash authority in bodies. Require one Idempotency-Key for mutations. CAS commands require one strong If-Match of the documented revision resource; reject missing/weak/wildcard/multiple values. Wire schemaVersion=1 is new; existing contracts do not change.

Every body has exactly schemaVersion/correlationId plus its listed fields. GUID correlation is nonempty and validated; GET correlation is server-generated. `label` is the bounded metadata defined above. All nullable fields are required and explicit null. No duplicate/unknown JSON fields, unsupported enum/version, coercion, extra query keys or conflicting Content-Length/Transfer-Encoding. Body max 16 KiB; frozen/detail response max 96 KiB; list max 64 KiB, 1–50 items, fetch limit+1, ascending createdAtUtc/ID and a same-scope cursor. Exceeding a result bound yields 503, not truncation. Overall 10 seconds, gate acquisition 1 second and gate-held stage 2 seconds including existing audit budget; no streaming/exports.
