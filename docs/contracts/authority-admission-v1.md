# Authority and protected admission v1 — accepted single-process pilot contract

Owners: [FEAT-IAM-001](../features/identity-access/features/authorize-resource.md), TEN/PRJ/INV fact owners and [FEAT-AUD-001](../features/audit-compliance/features/immutable-audit.md). Adopted by [ADR-0012](../decisions/0012-operator-pilot-runtime-foundation.md) for Foundation T01–T07 on 2026-10-20. It preserves the accepted I2.7 behavioral baseline and does not claim distributed revocation. No wire authority object is accepted from a client.

## Owner contracts and provenance

| Port / owner | Required internal result; missing/unknown always denies |
|---|---|
| CurrentSubject / IAM | Exact principal/session, current active status, boot/security revision and exclusive validity interval |
| Membership / TEN | Exact subject/tenant, active organization and membership, current revision and revocation/expiry |
| EffectiveAssignment / TEN | Exactly one applicable assignment for the requested action/scope in the first target.read slice; exact definition/revision and grantor provenance; ambiguous multi-grant resolution denies |
| RolePolicy / IAM | Referenced definition revision, exact permission, complete applicable denies/conditions and current policy revision |
| ProjectEnvironment / PRJ | Exact tenant/project/application/environment chain and classification/policy association; explicit resolved absence where project-only is supported |
| TargetOwner / INV | Stable target identity/lifecycle, tenant/project/environment association and current binding revision; contrary PRJ evidence denies |
| AuditAppend / AUD | Immutable stage-intent hash and durable append outcome; only a confirmed matching record supplies a receipt |

The approved initial lifecycle rule is Active-only for principal, tenant, membership, assignment, project, application, environment and target; Disabled/Suspended/Deleted/unknown states deny. Environment may be explicitly absent only for a project-scoped target whose PRJ/INV owners both affirm absence. Inventory evidence is separate from provider identity and from current authorization.

## Foundation command/query shapes and ownership

JSON envelopes use schemaVersion=1/correlationId as in the client handoff; IDs are opaque server-generated UUID references. Bodies reject unknown fields and never accept authoritative tenant, creator, revision or grantor values. Route tenant/resource references are selections verified against owner data. Mutations require Idempotency-Key and current ETag/If-Match for updates; changed body/key or stale revision gives a safe conflict. Limits: 128 KiB command body, names 1–128 characters, at most 50 list records per request. First target.read remains a single bounded result; general list/query responses need their own authorized query boundary and must not reuse a one-target permit.

All unsafe browser business commands also require authentication-v1's same-origin/Host/antiforgery controls. State changes use the writer gate, resolve current policy/owner facts through their ports and commit owned mutation plus required audit together before success. Until T06 implements that enforcer, T04/T05 HTTP routes stay unregistered; persistence/owner-contract tests do not authorize a placeholder route.

|---|---|---|
| TEN / initialize workspace | Offline typed manifest `{manifestId, principalId, organizationName, explicitResources, explicitGrants}` | Transactional owner-handler initialization with safe references; exact manifest hash replay or conflict; local founding authority audited, no remote route |
| TEN / list memberships | GET `/api/v1/me/organizations` | Current user's active memberships and only authorized tenant metadata; no platform directory fallback |

| TEN / suspension | POST `/api/v1/organizations/{org}/suspend` with If-Match/reason | `org.manage`; blocks protected tenant reads as well as writes, increments authority revision and audits |

| PRJ / environment | POST `/api/v1/projects/{project}/environments` `{name, classification, policyRevision}` | Classification enum Development/Test/Staging/Production is explicit; exact project owner and policy association required; rename cannot change classification |

| INV / target metadata/read | GET `/api/v1/targets/{target}`; later GET `/api/v1/targets/{target}/inventory` | `target.read` exact project/environment under U/D; `{targetId, projectId, environmentId?, kind, status, revision}` metadata only, later sanitized inventory schema |
| AUD / scoped history | GET `/api/v1/organizations/{org}/audit` with bounded cursor/filter | `audit.read` organization; authorized disclosure and tenant-safe cursor; first implementation may keep HTTP query disabled until its list-disclosure contract passes |

Create endpoints return 201/reference/ETag after state+audit commit; retries return the same persisted resource reference. Explicit environment absence is a typed owner result, not a failed lookup. Target association updates call PRJ and INV owner handlers in the same enlisted transaction while holding the writer gate; a mismatch/partial commit never activates a target. No direct cross-owner table read or second authority store is introduced.

First pilot principal/member/role-definition enrollment and workspace founding are offline, API stopped. Provision only explicit catalog grants at exact scopes; `project.manage` cannot mint `target.read` or `deployment.execute`. Initial read-slice supports exactly one effective assignment; roles are data, not if-role branches. Multiple assignments for other actions may coexist but ambiguous resolution for one action denies until an approved combination rule exists. Online invitations/email delivery and arbitrary role-definition editing are later increments, not hidden requirements for T04. TEN assignment ownership is accepted by ADR-0012; implementation remains pending.

Provisioning manifest schemaVersion=1 names the target instance, existing principal, tenant name, local symbolic project/application/environment/target definitions and explicit role-definition permission/scope lists. IDs are generated by owner handlers and resolved from those manifest-local names; no HTTP caller supplies founding IDs or authority. Reject unknown permission keys/scope types, platform grants and unsupported mutation capabilities. Store only the immutable nonsecret manifest hash/result references. Reusing its manifestId with changed content conflicts, even after partial/unknown completion; the transaction and exact result lookup settle recovery. No default role name implies a permission set.

The same U/D mechanism also governs Foundation queries with a **query-specific authorization callback**, not a fabricated target.read permission. IAM self/me validates only the current subject/session and personal metadata; it does not require a tenant. The initial organization selector first resolves the current subject's memberships and emits only minimal self membership/organization references; tenant names/details require current `org.read`. Catalog queries apply `project.read` to every emitted resource and revalidate the exact bounded candidate set and revisions at D. No unfiltered list is exposed before per-row authorization. Each list is a new invocation, max 50 records with no continuation permit; subsequent pages resolve current authority anew. AUD HTTP history remains disabled until its own query callback passes the same output/race proof. IAM introduces the common technical gate for self/authentication in T03; T06 extends the same gate to TEN/PRJ/INV writers, not a second lock.

Internal API uses owner contract DTOs and an enlisted transaction context supplied by composition; business Contracts expose no EF DbContext/Npgsql connection. Infrastructure adapters enlist in the same PostgreSQL transaction through a narrowly scoped technical unit-of-work service. Each owner alone reads/writes its tables. Session activity touches do not change a revocation/security revision, but cannot extend absolute expiry, revive expired idle authority or race a committed revoke. Domain-invalidating changes always increment the corresponding revision, including change-and-change-back.

## Single-writer assumptions, enforced before admission

The first pilot permits exactly one API process under the designated local operator OS account and database. Resolve the canonical private data directory from an installation UUID persisted by the offline installer; pin/check the instance/database identity and allow no per-launch lock-directory override or symlink alias. Hold an exclusive OS process lock on that directory for the entire process lifetime. An already-locked instance or conflicting identity refuses startup. Offline provisioning, migrations and recovery require the same exclusive lock and API shutdown. Do not implement automatic failover, alternate instance registrations for the same database, remote authority writers or live manual DB edits. PostgreSQL/OS administrators remain trusted operational actors; this protocol does not defend against privileged database tampering or hostile installation operators.

All authority-changing owner handlers, including account/session disable/logout, membership/assignment/definition changes, tenant suspension, project/environment policy or target reassignment, must use one **fair, writer-preferring reader/writer admission gate** in the API process. A pending writer prevents new read admissions until it completes or times out. The gate is a technical primitive; it contains no role, tenant or owner-table logic. An authority mutation's effective point is its durable transaction commit while holding the writer gate, and its success response follows that point. Failed/unknown commits are not acknowledged as successful revocations.

Every authority writer must be enumerated/tested in a registry before its endpoint is enabled. There are no event-driven/cache writers in this first scope. Time expiry is checked on each boundary and does not depend on a scheduled writer. A worker that can invalidate authority, a second API host, live DB maintenance or a new disclosure channel **invalidates these assumptions** and requires a replacement protocol before enablement.

## Exact protected read protocol

1. Resolve untrusted route selection, validate shape and acquire a read admission under the bounded request deadline. Under the gate, call owner ports for current subject, tenant, assignment/policy and resource chain. These are authoritative owner reads, not dashboard projections. All owners share the single-writer discipline; queries are sequentially coherent because invalidating writers cannot commit while the gate is held. Expiry/time validity is still rechecked independently.
2. Evaluate the accepted permission/scope predicate. For an eligible request, AUD durably appends a U-intent bound to invocation, principal/session/tenant/target/scope, selected revisions and exact action. Await commit confirmation while holding the gate. Unknown/rejected append denies; append success alone is not U.
3. Recheck cancellation, trusted monotonic/UTC time and earliest authority expiry. **U is the synchronous admission of one exact typed read into the trusted adapter**, while the gate is still held. Do not queue an unbound request for later retargeting. Release the gate after admission; await provider I/O outside it into a private bounded buffer. U grants no right to disclose later.
4. Obtain a new read admission for D. Re-resolve every required authority and compare the entire subject/scope/selection/revision binding with U. Any intervening change discards the old result, even if a new grant might permit a fresh request. No automatic retry is an extension of the old permit.
5. AUD durably appends a distinct D-intent bound to the exact validated result digest/size and current decision; it stores no response payload. After commit, recheck cancellation and time at the commitment boundary. **D is the caller-bound response committer's acceptance of the validated bounded buffer for irreversible transport handoff**, under the same read admission. No body/header containing protected data may be written before this step.
6. Keep admission until the bounded write/flush attempt completes or is aborted. Release in `finally`; no cache publication or retry after unknown partial delivery. If an invalidating writer was already pending, a new D cannot overtake it. If D already holds admission, that writer waits and becomes effective only at its later durable commit. Already handed-off bytes may arrive after that commit; this accepted residual is bounded by ADR-0012 and is not atomic/retractable network delivery.

No streaming, partial-result fallback, pagination continuation, WebSocket, export, shared result cache or independent background disclosure is enabled here. Every later page/export must obtain a new protocol contract. Framework handoff, abort and writer interleavings require an instrumented adapter/HTTP proof; if the framework can flush protected bytes early or the gate cannot bound admission, keep positive ingress denied and report the defect. Do not redefine D as audit commit to pass the proof.

## Bounds and availability trade-offs

Accepted initial bounds: at most 16 active protected invocations; result at most 256 KiB/200 sanitized records; per-provider read deadline 5 seconds; overall invocation 10 seconds; gate acquisition at most 1 second; each gate-held U/D stage at most 2 seconds including audit/write, with an audit append budget of 1 second. Authority facts are read for each boundary with **no authorization cache or stale grace**. Each stage uses the earliest underlying expiry and a monotonic deadline; over-budget results deny/abort rather than truncate into success. Cancellation/abort must unwind outstanding commit attempts before releasing the gate; if cleanup cannot establish that, close the pilot host to new admissions rather than releasing a fence while a writer/body operation can still run.

This deliberately bounds revocation delay at the cost of failed reads during audit/transport contention. Values are approved limits, not measured performance claims. A test must show bounded writer progress and no more than the declared concurrent capacity; do not weaken ordering or silently increase payloads to improve throughput.

Trusted time uses a nondecreasing effective UTC combined with monotonic request deadlines. Persist an IAM-owned last-admitted UTC floor with each audited commitment; startup checks it before admission. A clock step backward never reduces effective UTC or makes an observed-expired grant usable; disagreement/rollback over the approved one-second threshold closes new admissions. The floor is not caller-provided evidence. Test clock rollback across restart as well as within one process; privileged OS time manipulation and historical database restore require explicit offline reconciliation, not an expiry grace period.

## Audit v1 intent and outcome

Internal immutable fields: schemaVersion=1, intentId, invocationId, stage(U/D/mutation/outcome), subject reference, tenant/resource references where applicable, permission, scope, policy/authority revision binding, safe reason, occurredAtUtc, correlationId, and D result digest/size without payload. AUD persists server-generated identity and canonical nonsecret intent hash. Unique `(intentId, hash)` replay returns the existing durable receipt; same intentId/different hash rejects. Append outcomes remain the AUD-owned `durable`, `rejected`, `unavailable`, `unknown` semantics.

Authentication/startup records are explicitly global/self-scoped rather than assigned a fake tenant. Tenant audit queries exclude those records; future platform/security access requires its own accepted permission and redaction contract. Tenant-owned rows always carry validated tenant IDs and resource associations; no null-tenant fallback selects global authority.

No U receipt satisfies D; no old receipt authorizes a new attempt. Unknown ACK is reconciled through exact intent lookup under a fresh admission; discovery that the intent exists does not prove protected work occurred. An actual stage outcome may be Completed/Denied/Cancelled/Unknown, separately recorded; crash after intent is Unknown until evidence resolves it. Do not replay protected work to manufacture a completion outcome.

Security/privileged mutations and successful authentication require their owned state change and AUD append in one enlisted database transaction. A business module calls AUD through a port, not its tables. Denial audit is bounded best-effort (100 ms, no unbounded retry queue); denial is never delayed indefinitely or converted to permit. Minimum audit retention is 90 days; the app role cannot UPDATE/DELETE/TRUNCATE audit rows. The reviewed offline AUD migration explicitly revokes those grants on each AUD table, overriding ADR-0011's generic future-table DML defaults while retaining INSERT/SELECT and required sequence access. Tests must verify actual grants. Migration/retention authority remains offline; no automatic purge is introduced. Audit is not tamper-proof against the database owner.

## Required proof matrix

Test revoke before U, between U/D, writer queued before D and D held before writer; expiry at both commitments; policy/target rebind and change-back revisions; disabled/suspended lifecycle; owner not-found versus resolved absence; denied grant ambiguity; audit ACK loss/crash/conflicting replay; DB outage; provider timeout/oversize; Host/tenant substitution; response partial failure; process restart and concurrent second process refusal. Assert adapter calls and protected output counts, not just return codes. Source architecture tests must reject cross-owner context/SQL access and production fake adapters. These are required future tests, not executed evidence.

## PR #10 implementation correction — 2026-10-22

The single-process mechanism and bounds above remain unchanged. The shared technical gate now queues overflow after 16 active readers on both immediate entry and queue drain, preserving writer preference. Unknown audit/owner commits and unresolved exceptions at the transaction port irreversibly close the current gate, reject queued/future admissions, and cannot reopen it by releasing an existing lease. Restart creates a fresh gate only after the normal boot/session-invalidation protocol; this is no claim that restart proves a particular earlier command succeeded. Best-effort credential-denial recording receives a dedicated linked 100 ms deadline; failed-password counter/lockout mutation remains mandatory and cannot be treated as a successful authentication. Gate closure is covered by queued-admission tests and actual committed-mutation/lost-ACK fixtures.

PR #10 round-2 correction: audit enlistment is setup-only and must not run owner mutation or commit. A failure/cancellation before the commit-capable protocol is entered propagates to the existing denial/unavailable handling without closing the shared gate. Unknown outcomes or exceptions after protocol handoff still close admission. Disposing an already-resolved audit context does not itself establish an unknown commit. No numeric bound or wire/schema behavior changes.

## T04 owner-port implementation note — 2026-10-22

The accepted v1 external protocol and ownership remain unchanged. Internal BCL-only IAM Contracts now provide exact-current role definitions, active-principal reads, trusted clock and offline-lease ports; TEN Contracts provide typed internal owner commands/results, minimal self-membership references, current-subject and trusted scope-owner ports. These are not HTTP request schemas: tenant/resource IDs select data and must be resolved against owners; subject and grantor always come from trusted adapters. No HTTP schemaVersion migration or consumer rollout is performed by this internal addition.

TEN persistence/handlers and IAM definition publication use the shared gate and AUD transaction ports in isolated tests. Runtime injection of subject/resource/lease adapters and U/D enforcers remains T05/T06; none has a permissive default. The internal effective-assignment read requires its trusted caller already to hold common admission and returns facts, not a transferable permit. The same-process writer boundary, exact scoped ceiling, current revisions, explicit deny and fail-closed ambiguity are preserved. No invitation, platform grant, new resource permission, provider read or output-disclosure authority is introduced.

## T05 internal owner-port implementation — 2026-10-22

Public HTTP v1 envelopes and ownership decisions above remain unchanged. Internal PRJ Contracts now expose CatalogCommand/Fact, exact ProjectOwnership (ResolvedAbsent versus ResolvedPresent environment), TargetAssociation and required trusted catalog-authority/environment-policy ports. INV Contracts add metadata-only target commands/facts. Contracts remain BCL-only; EF connections/transactions are confined to Infrastructure/Host.

The technical Host coordinator acquires the same injected writer gate and enlists PRJ/INV/AUD in one PostgreSQL transaction. Owners alone validate/read/write their tables. Target facts require current matching owner and association revisions; a missing lookup never establishes environment absence. Replay binds command type/body and current trusted principal, with fresh authority before receipt lookup. Unknown commit is unavailable and closes admission; setup failure occurs before commit protocol and cannot close it. No new HTTP field/schemaVersion or public consumer migration occurs. These owner facts are not a U/D permit; T06 must compose current session/tenant/policy and caller-bound disclosure.

PR14 implementation clarification — 2026-10-23: TEN's EffectiveAssignment/ScopedGrant expiry denotes the earliest finite expiry over the selected assignment and all validated provenance sources, not only the leaf's stored timestamp. A null deadline means a valid wholly unbounded chain; an invalid chain returns no authority. Existing U/D earliest-expiry checks and delegation ceilings consume the same resolved value. Shape/version, single-process admission, cancellation, audit and already-accepted bounded-transport semantics are unchanged.

PR14 P2 implementation clarification — 2026-10-23: a fresh offline bind requires an active current policy with effectiveFromUtc <= trusted now and no expiry or expiresAtUtc > trusted now. Validate before staging and revalidate after AUD staging, before commit. Rejection rolls back all staged owner/history/receipt/audit changes without closing admission for a known pre-commit result. This does not restrict legitimate inactive policy publication or exact already-committed receipt replay, which precedes mutable validity checks. Existing schemas and authority protocol are unchanged.
